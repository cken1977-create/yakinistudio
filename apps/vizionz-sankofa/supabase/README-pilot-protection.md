# VS pilot protection — database migrations

Built Oct 16–17, 2026 on branch `vs-pilot-protection`. **Not applied to the live project** (`iksilqmhrgbxhxweymst`).

| File | What it does |
|---|---|
| `migrations/…0100_vs_roles_and_scoped_rls.sql` | `vs_operators.access_role` (executive, operator, case_manager, leadership_readonly). Replaces the "any signed-in user sees everything" policies with role + caseload policies. Case manager ↔ caseload link = `staff.auth_user_id` → `participants.primary_case_manager_id`. Existing principals are backfilled to `executive`. |
| `…0200_vs_audit_trail.sql` | Triggers on every participant table write to `vs_audit_log` (who, role, old row, new row, when). UPDATE/DELETE/TRUNCATE revoked and blocked by trigger. `vs_log_event()` for views, exports, Intelligence questions, sensitive reveals. |
| `…0300_vs_consents.sql` | `vs_consents` (scope, language, form version, guardian, interpreter, expiry, revocation). Terms immutable; revoke-only; no deletes. `vs_has_active_consent(participant, scope)`. |
| `…0400_vs_sensitive_fields.sql` | `participant_sensitive`: Medicaid ID, SSN, DOB encrypted with pgcrypto AES-256, key in Supabase Vault (`vs_pii_key`, generated by the migration). No direct table access. `vs_get_sensitive()` masks by role; reveals are logged. Plain DOB / SSN / Medicaid writes are moved into the encrypted table automatically. |
| `…0500_vs_client_flow_and_voice.sql` | Client-flow stage + `participant_stage_events` (timestamp + who), `vs_stage_summary` view, returning-client flag (re-entry after exit, or a new intake matching email/phone), per-user voice settings (wake phrase OFF by default). |
| `…0600_vs_obr_readiness.sql` | OBR (Organizational Behavioral Readiness): VS's own onboarding/intake for Yakini's BRSA standard. `vs_obr_profiles` (the VS intake: governance, staff, policy, financial), `vs_obr_evidence` (checklist with attestation), `vs_obr_evidence_files` (uploaded evidence metadata; files in the private storage bucket `vs-obr-evidence`, executive/operator only), `vs_obr_ratings` (evaluator decisions exactly as issued, with standard version; append-only), and the read-only monitor export `vs_obr_monitor_summary()` (service_role only). Executive/operator write, leadership read-only (no file downloads), case managers no access. Audited. |
| `…0700_vs_coalition_partners.sql` | Coalition partners on top of `organizations` (partner / both): `vs_partner_agreements` (MOU/data-sharing, dates, signatories, participant-data flag), `vs_partner_checkins` (summary, next due → `organizations.next_touch_due`), `vs_partner_programs` (shared program/cohort coordination). Case managers can read agreements and shared programs, not check-ins. Audited. |
| `…0800_vs_staff_full_name.sql` | Fixes an existing live bug: the app selects `staff.full_name`, which doesn't exist on live (cohort list empty, staff pickers blank). Adds it as a generated column from first + last name. |

## OBR monitoring export (for Clarence's side)

`public.vs_obr_monitor_summary()` returns one JSON document with the VS OBR
status, checklist completion (`total`, `complete`, `verified`,
`percent_complete`), each checklist item with its uploaded-file metadata
(file name, type, size, who uploaded, when) and the latest evaluator decision.
It contains no participant data, no free-text notes, no storage paths and no
file contents. It is `SECURITY DEFINER` and executable by `service_role` only
(revoked from `anon` and `authenticated`).

How Mission Control / Kamili would read it (server-side only, never in a browser):

```bash
curl -s -X POST "https://iksilqmhrgbxhxweymst.supabase.co/rest/v1/rpc/vs_obr_monitor_summary" \
  -H "apikey: $VS_SERVICE_ROLE_KEY" -H "Authorization: Bearer $VS_SERVICE_ROLE_KEY" \
  -H "Content-Type: application/json" -d '{}'
```

or, with supabase-js on a server: `createClient(url, serviceRoleKey).rpc('vs_obr_monitor_summary')`.
Poll it on a schedule (e.g. hourly); `generated_at` marks the snapshot time.
The Mission Control side is not built here. When OBR is separated from the VS
system later, this function is the contract to keep (`schema_version: 1`).
